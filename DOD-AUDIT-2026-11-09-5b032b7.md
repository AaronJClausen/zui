## Summary

All of a frame's data lives in one preallocated `Memory` block (about 5 MiB at the default limits). Most of it is the two in-flight `Frame`s, each about 1.9 MiB. The hot loops are the layout passes and emission, each one linear sweep over up to 4,096 elements. They are already stored as struct-of-arrays and tuned with measurements, so the per-element sweeps have little left to give. The real costs sit next to those sweeps, in paths the benchmarks never run:

1. **The layer sort.** Any frame with a floating element runs `std.sort.block` over every 80-byte `RenderCommand`. One tooltip in a 3,000-command frame costs **124 µs** if it is emitted mid-frame and **446 µs** if it is emitted first. That is longer than the whole 4,096-box layout (84 µs). A stable split by layer does the same job in about **5 µs**, and in **0 µs** when the commands are already in order.
2. **The id → rect table** (`Results.entries`) has 32-byte slots, 256 KiB at the default limits, and is filled by random inserts during emission. A table of 2-byte indices pointing into a dense entry array cut 4,000 cold inserts from **28.4 µs to 8.9 µs**.
3. **Warm text re-wraps every frame.** Every unchanged text at an unchanged width is wrapped again from its bytes each frame. The warm text wall spends about 50 µs more in layout than the single-line case. Caching the wrapped lines could recover much of that, but this one is not measured yet.

Every other item below is small, and so labelled.

## Findings

### 1. The layer sort moves every command through a block sort

- **Where:** `src/emission.zig:71-75` (`std.sort.block(Ui.RenderCommand, ..., lowerLayer(Ui))`). Commands are pushed in `Emitter.push`, `src/emission.zig:119-129`.
- **Data today:** `RenderCommand` is 80 B. The comparator reads `z` (2 B). The sort runs over all `command_count` commands (up to 8,192) as soon as one floating element exists. Nearly every command has `z = 0`; only the floating subtrees have another z, and there are few of them.
- **Why it costs:** `std.sort.block` (WikiSort) is stable and in place, so out-of-order runs are fixed with rotations that move whole 80 B elements, over O(log n) merge levels. I measured it on 80 B elements with one run of 20 `z = 1` commands (a tooltip):

  | 3,000 commands, tooltip emitted… | block sort | stable split (sketch below) |
  |---|---|---|
  | first | **446.3 µs** | 5.4 µs |
  | in the middle | **123.9 µs** | 5.4 µs |
  | last | 6.1 µs | 5.3 µs |

  At 8,000 commands with the tooltip in the middle, the block sort takes 613 µs. Any of these numbers is larger than the 84 µs the 4,096-box layout takes. A tooltip or menu declared early in the tree (a toolbar dropdown, a header popover) is the worst case. No benchmark scene has a floating element, so `bench --check-targets` and `counts` cannot see this.
- **Proposed shape / algorithm:** Most commands are in layer 0, so make layer membership decide where a command is stored, instead of sorting by a key afterwards. The layer-0 commands grow from the front of `render_commands`, and the others grow from the back, in the same array. Capacity and the `max_render_commands` accounting stay as they are.

  ```zig
  fn push(self: *Self, command: Ui.RenderCommand) void {
      const frame = self.frame;
      self.attempted_commands += 1;
      if (frame.command_count + self.layered_count >= frame.render_commands.len) return self.reportFull(command.id);
      if (command.z == 0) {
          frame.render_commands[frame.command_count] = command;
          frame.command_count += 1;
      } else {
          self.layered_count += 1;
          frame.render_commands[frame.render_commands.len - self.layered_count] = command;
          self.layers_out_of_order = self.layers_out_of_order or command.z < self.highest_layered_z;
          self.highest_layered_z = @max(self.highest_layered_z, command.z);
      }
  }

  fn joinLayers(self: *Self) void {
      const frame = self.frame;
      const layered = frame.render_commands[frame.render_commands.len - self.layered_count ..];
      std.mem.reverse(Ui.RenderCommand, layered);
      if (self.layers_out_of_order) std.sort.insertion(Ui.RenderCommand, layered, {}, lowerLayer(Ui));
      const below_count = countBelowLayerZero(layered);
      // Negative layers paint first: shift layer 0 up by `below_count` and copy them in front.
      ...
  }
  ```

  The common case is a few `z > 0` commands with no negative layer. That costs one copy of the tail, about `layered_count × 80 B`, and no pass over layer 0. If that bookkeeping inside `push` is too much, a simpler first step is to skip the sort whenever the commands are already in order: track `max_z_so_far` in `push` and set a flag when a lower z follows. That alone makes "tooltip last" free.
- **SIMD surface:** None needed. The point is to stop moving the 97% of commands that are already in place.
- **Requirement changes, if any:** None. Paint order stays exactly what a stable sort by `z` gives. For a long tail, the insertion sort can be replaced by `std.sort.block` on the tail alone.
- **Risks / when this would be wrong:** A frame where most commands are floating, such as a canvas of floating cards, still has to sort a long tail. It is still cheaper than today, because the tail is all that gets sorted. The `first_dropped_id` reporting must stay the same when the two ends meet.
- **How to verify:** Add a scene to `bench/scenes.zig`: the box tree plus one floating, decorated tooltip declared first, and another with it declared last. Then run `zig build bench-compare -- <base>`. The Tracy zone `.sort_layers` already brackets this code.

### 2. The id → rect result table is 8× wider than it needs to be

- **Where:** `src/interaction.zig:159-198` (`Results.entries`, `insert`, `find`). Inserts come from `src/emission.zig:179`, once per element with an explicit id. Lookups come from `widgetState`, `rectOf`, `pointerLocal`, coasting and zoom (`src/context.zig:1614, 1635, 1773, 1914, 2151, 2160`).
- **Data today:** `Entry { hash: u64, rect: Rect, region: u32 }` is 32 B. There are `nextPowerOfTwo(2 × max_elements)` slots: 8,192 at the default limits, so **256 KiB**, inside a `Results` of 508 KiB. Every insert is a random write and every `find` a random read, against a frame working set of about 2 MiB that has just been streamed through layout, so these probes miss L1 and usually L2.
- **Why it costs:** Each probe touches one 64 B line that holds two slots. The frame's own `id_table` already shows the tighter shape: `[slots]Index` at 2 B, with `element_id` checked through the index. I measured both shapes on random 64-bit hashes, cold:

  | ids per frame | 32 B slots | 2 B index + dense entries |
  |---|---|---|
  | 500 | 2.6 µs | 3.8 µs (includes a full 16 KiB clear) |
  | 4,000 | **28.4 µs** | **8.9 µs** |

  At 500 ids the index version lost only because the test cleared the whole index table. Clearing just the used slots, as `clear` does today with `used_slots`, takes that cost away.
- **Proposed shape / algorithm:**

  ```zig
  slot_entry: [table_slots]u16,      // or the Context's Index type; maxInt marks an empty slot
  entries: [max_regions]Entry,       // dense, in emission order
  entry_count: u32,
  entry_slot: [max_regions]u32,      // the slot each entry took, so `clear` resets only those

  pub fn insert(self: *Self, hash: u64, rect: style.Rect, region: u32) void {
      var slot: usize = @as(usize, @truncate(hash)) & (table_slots - 1);
      while (self.slot_entry[slot] != empty) : (slot = (slot + 1) & (table_slots - 1)) {
          const existing = self.slot_entry[slot];
          if (self.entries[existing].hash == hash) return self.overwrite(existing, rect, region);
      }
      self.slot_entry[slot] = @intCast(self.entry_count);
      self.entry_slot[self.entry_count] = @intCast(slot);
      self.entries[self.entry_count] = .{ .hash = hash, .rect = rect, .region = region };
      self.entry_count += 1;
  }
  ```

  Also consider copying `RegionFlags` (1 B) into `Entry`, so that `widgetState`'s `regionFlags` (`src/interaction.zig:201-205`) skips its second dependent miss into `regions[entry.region]`.
- **SIMD surface:** None. This is a locality fix.
- **Requirement changes, if any:** None. `Results` keeps its separate lifetime from the frame.
- **Risks / when this would be wrong:** A frame with very few ids gains nothing. Keep the clear proportional to `entry_count`, never to the table size.
- **How to verify:** None of the benchmark scenes gives elements ids, so add one: 4,096 boxes, each with `.id = .indexed("cell", i)` and `.interactive = true`, plus a pass that calls `widgetState` on each. Compare `emit` zone time and `counts` instruction totals.

### 3. Unchanged texts are re-wrapped from their bytes every frame

- **Where:** `wrapTexts`, `src/layout.zig:650-669`, calling `wrapLines`/`wrapWords` in `src/text.zig:597-702`.
- **Data today:** For each text whose `preferred_width` exceeds its width, `wrapWords` runs `WordIterator` over the text again (a 16-byte SIMD separator search), reads one f32 run width per word, and greedily appends 12 B `Line`s. The warm text wall (1,000 texts of about 40 bytes, two or three lines each) takes 97.8 µs in layout. The same texts on one line take 48.1 µs. The difference covers wrapping plus emitting about 1,500 more line commands.
- **Why it costs:** In a steady-state frame, the bytes, key, wrap mode and width are all identical to the previous frame, so the result is too. The string cache (`text.zig:276-285`) already proves the text is unchanged: that is what a warm hit means. Only the width is not checked.
- **Proposed shape / algorithm:** Treat the wrap result as baked data. Next to `CachedString`, keep `wrapped_at: f32` and the line breaks as offsets relative to the text, `[max_cached_lines]struct { start: u16, end: u16, width: f32 }`, only for texts with few lines. On a hit whose width is within `tolerance` of `wrapped_at`, `wrapTexts` copies the lines with `base` added and skips the word walk. On a mismatch it wraps as today and stores the result.
- **SIMD surface:** None. This removes the work instead of widening it.
- **Requirement changes, if any:** Each string-cache entry grows by `max_cached_lines × 8 B + 4 B`. With 4 lines, 36 B per entry, or 72 KiB at 2,048 entries. That is a memory-budget decision.
- **Risks / when this would be wrong:** Layouts whose widths change every frame (an animated resize) never hit, and pay a store. Texts with many lines should not be cached this way. How much this saves is an estimate: I did not split the 50 µs between wrapping and emission.
- **How to verify:** Look at the Tracy `.wrap_text` zone in the warm text wall before changing anything. If it is under about 10 µs, drop this finding.

### 4. Cache probes walk wide entries; independent text lookups are not overlapped

- **Where:** `LruTable` in `src/text.zig:184-273`, used by `MeasureCache.findString` (once per text) and `lookup`/`claim` (once per word on a miss).
- **Data today:** A string entry is 104 B and holds the key, `last_used`, metrics and 16 run widths. A probe window of 8 steps can touch 8 cache lines to compare 8 keys. A miss (`lookupOrClaim`) always walks the whole window to find the least recently used entry. A segment entry is 24 B, so its window is 3 lines.
- **Why it costs:** On the `1000 new strings` scene (201 µs), every text misses the string cache, which walks up to 8 lines, and then probes the segment cache once per word. Each probe is an independent random load, but the loop in `measureTexts` exposes them one at a time.
- **Proposed shape / algorithm:** Split each table hot/cold: put `keys: [entry_count]u64` and `last_used: [entry_count]u32` in arrays of their own, and the values alongside. Then the 8 keys of a window fill one 64 B line (two at most when the window wraps a line boundary). In `measureTexts`, hash text `i + 4` and `@prefetch` its key line before resolving text `i` (group prefetching).
- **SIMD surface:** The window's 8 keys can be compared against the probe key in one `@Vector(8, u64)` compare, or two 4-lane compares on AVX2.
- **Requirement changes, if any:** None.
- **Risks / when this would be wrong:** In warm frames, a hit reads the value right after the key, so the split adds a second line per hit unless the prefetch covers it. Measure the warm text wall too.
- **How to verify:** `bench-compare` on `1000 texts, cold cache`, `1000 new strings` and `1000 texts, warm cache`; L2 misses (`perf stat -e l2_rqsts.miss` in the Linux container).

### 5. Hit testing: four scans per press, each reading under half of every region

- **Where:** `refreshHover`, `longPressOwner`, `recognizerAt` and `startZoom` each call `Results.topmostAt` with the same point for one `pointer_down` (`src/context.zig:1357-1368`). The scan itself is in `src/interaction.zig:209-216`.
- **Data today:** `Region` is 40 B. The scan reads `bounds` (16 B) and `z` (2 B), so 45% of each line is useful, and it branches on every region.
- **Why it costs:** I measured one scan over 4,096 regions at 1.5 µs. With edge arrays (`left`, `top`, `right`, `bottom`, `z`) and 8-lane compares, it took 0.7 µs. A press costs four scans; a frame costs one per hovering contact.
- **Proposed shape / algorithm:** First, and cheapest, hit-test once per `pointer_down` and pass the region index to the three callers. After that, if many regions ever matter, emission can write `RegionEdges` SoA arrays next to `regions`.
- **SIMD surface:** 8 × f32 per compare on AVX2; the hits become a bitmask, then `@ctz` over the set bits.
- **Requirement changes, if any:** None.
- **Risks / when this would be wrong:** The absolute saving is about 1–4 µs per press, so this is low priority unless real apps declare thousands of interactive regions.
- **How to verify:** A microbenchmark of `topmostAt` over 4,096 regions, and a `counts` scene with pointer-down events.

### 6. Child walks are a chain of dependent loads (speculative)

- **Where:** `Frame.Children.next` (`src/context.zig:487-492`) and `FlowChildren` (`src/layout.zig:76-81`). They are used by `distribute`, `grow`, `shrink`, `placeChildren` and the wrapping functions.
- **Data today:** The next child is `subtree_end[child]`, so each step's address depends on the load before it. For leaf children this is `child + 1`, but the CPU cannot know that without the load. `distribute` on the main axis walks the children two or three times (sum, then grow), and `position` walks them again.
- **Why it costs:** For a parent with 4,000 leaf children, every walk is about 4,000 L1-latency-bound steps, at roughly 4–5 cycles of critical path each. The `4000 children of one parent` scene takes 61 µs of layout. I have not measured how much of that is the chain.
- **Proposed shape / algorithm:** After declaration, build a CSR layout in two linear passes: `first_child_slot[parent]` as the prefix sum of `child_counts[parent].all`, then scatter each element into `child_list` under its parent. Child walks then become `for (child_list[first..][0..count]) |child|`, with independent loads that can also be gathered.
- **SIMD surface:** With a contiguous child list, the sums and maxima in `distribute`'s cross-axis loop become reductions over gathered sizes. Gathers are slow, so expect only modest gains.
- **Requirement changes, if any:** It adds `max_elements × 2 B` per frame, and two passes per frame.
- **Risks / when this would be wrong:** The box tree, where each parent has one or two children, would pay for the build and gain nothing. The comments in `layout.zig` already record that restructuring these passes cost 3–17% before, so do this only if a profile of a wide scene points at `Children.next`.
- **How to verify:** Check `perf` cycles attributed to `Children.next` in `4000 children of one parent` before writing any code.

### 7. Render commands are fat for line-heavy frames (low)

- **Where:** `RenderCommand`, `src/commands.zig:31-36`; the text payload, `src/commands.zig:98-102`; `emitText`, `src/emission.zig:233-253`.
- **Data today:** Each command is 80 B. A text line carries a 16 B slice, a 24 B copy of its `TextStyle` and a line number. A text-heavy frame writes about 2,500 × 80 B = 200 KB of commands, and every renderer reads all of it.
- **Proposal:** Only if renderer bandwidth ever shows up in a profile: refer to the style through an index into a per-frame style table, which roughly halves the text payload. This is an API change for every renderer, so it is listed only for completeness.

## Already in good shape

These are already data-oriented. Leave them alone:

- **The `Frame` is struct-of-arrays.** `size`, `min_size`, `position`, `parent`, `flags`, `child_counts` and `subtree_end` are separate arrays, and every layout pass streams only the ones it needs (`src/context.zig:375-405`).
- **Elements are stored in declaration order.** That is depth-first order, so "first child = next element" and "next sibling = `subtree_end`" hold without any pointers. The `fit` pass runs backward and adds each child into its parent, so it never walks a child list (`src/layout.zig:130-174`).
- **Fields are sized and packed.** `ElementFlags` is `packed struct(u16)`, `Index` is the smallest whole-byte integer, the two `ChildCounts` are bumped with one add, `Sizing` has no padding bytes, and `Layout` (56 B) has a test pinning its size.
- **Unused features cost nothing.** A missing feature or payload type sizes its arrays to zero and drops the code path at compile time (`starts_line`, `gestures`, `texts`, `images`).
- **Nothing allocates after `init`,** and the benchmark enforces it. One aligned block holds everything (`required_bytes`).
- **Measured inline and out-of-line choices.** Rare paths are kept out of line with `@call(.never_inline, …)`, and the comments record the measured reason for each (`clampedScrollOffset`, `sizeFloatingChildren`, `growFromMin`).
- **Text separators are found 16 bytes at a time** with a vector compare and `@ctz` (`src/text.zig:36-49`).
- **Warm text costs one probe.** The string cache keeps a whole text's metrics and run widths, so a warm text needs one hashed probe instead of one per word.
- **`Results.clear` resets only the used slots** (`used_slots`), not the whole table.
- **State-table eviction was measured and needs nothing.** It scans 96 KiB at a 96 B stride every `beginFrame`, and took about 0.5 µs warm or cold, because the prefetcher keeps up with the stride. A key/age split timed no faster (0.8 µs, within timer resolution), so leave it unless `state_slots` grows by an order of magnitude.

## Suggested order of work

1. **Add the missing benchmark scenes first** (see the measurement plan). Findings 1 and 2 are invisible to the current suite.
2. **Finding 1, first step:** skip the sort when the commands are already in order (a flag set in `push`). It is tiny and makes the common "tooltip declared last" case free.
3. **Finding 1, full change:** store the non-zero layers from the back of the array, and sort only that tail.
4. **Finding 2:** the index table plus dense entries for `Results`, with `RegionFlags` copied into `Entry`.
5. **Finding 5, first step:** one hit test per `pointer_down`. It is a few lines.
6. **Finding 3:** check the `.wrap_text` zone, then build the wrap cache if it is worth it.
7. **Findings 4 and 6:** only after profiling the cold-text and wide-tree scenes.

## Measurement plan

**Benchmarks to add to `bench/scenes.zig` before changing anything:**

- **`box tree + tooltip first` and `box tree + tooltip last`:** the 4,096-box tree with one floating element (`z = 1`, background, a text child), declared as the first child of the root and as the last. These exercise `.sort_layers`.
- **`4096 interactive boxes with ids`:** the box tree with `.id = .indexed("cell", i)` and `.interactive = true`, and a call to `ui.widgetState(id)` per element during declaration. This exercises `Results.insert` and `find`.
- **`pointer down over 4096 regions`:** a record with one `pointer_down` each frame over the scene above. This exercises `topmostAt`.

**Counters and tools:**

- **Tracy zones that already exist:** `.sort_layers`, `.emit`, `.wrap_text`, `.measure_text` and `.evict_state` split `endFrame` and `beginFrame` without new instrumentation (`zig build bench -Dzui-tracy=true`, or an app built with `zui_tracy`).
- **`zig build counts -- --compare <file>`** in the Linux container, to check instruction totals per scene. CI fails on more than 2% growth, which also guards findings 4 and 6 against regressions.
- **`perf stat -e cycles,instructions,L1-dcache-load-misses,l2_rqsts.miss,branch-misses`** in the same container (`--security-opt seccomp=unconfined`) for findings 2 and 4. Expect L2 misses in `emit` to fall with finding 2, and branch misses in `topmostAt` to fall with the SoA scan in finding 5.
- **`zig build bench-compare -- <base>`** on this machine for every change that claims a speedup, as the project requires.

The microbenchmarks quoted above (sort, results table, hit test, eviction) were standalone Zig programs that model the same element sizes and access patterns. They show the order of magnitude, not exact figures for zui, so each finding still needs its in-tree `bench-compare`.
